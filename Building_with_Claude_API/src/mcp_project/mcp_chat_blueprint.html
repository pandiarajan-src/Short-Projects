MCP Chat — System Blueprint

How main.py, mcp_client.py, mcp_server.py, and the core/ modules fit together to let a terminal user chat with Claude while Claude reads and edits documents through an MCP server.

01 Purpose

MCP Chat is a terminal chat application that lets a user converse with a Claude model while giving that model access to external tools, resources, and prompts exposed by one or more MCP (Model Context Protocol) servers.

The bundled MCP server (mcp_server.py) is a small "document store" service: it holds a handful of fake documents in memory and exposes them three ways:

PrimitiveExposed asWho calls it
Toolsread_doc_contents, edit_documentClaude (via tool-use)
Resourcesdocs://documents, docs://documents/{doc_id}The client directly (no model round-trip)
PromptsformatThe user, via /command

The CLI wraps this in a REPL that supports three input shapes:

SyntaxMeaningHandled by
plain textNormal chat turn, sent to ClaudeChat.run
@doc_idInlines a document's contents as contextCliChat._extract_resources
/command doc_idRuns an MCP prompt, e.g. /format plan.mdCliChat._process_command

Architecturally this is a minimal reference implementation of Host → Client → Server, plus a thin agent loop (Chat) that repeatedly calls Claude and feeds tool results back until Claude produces a final answer.

  • main.py is the composition root: it loads env vars, spawns the MCP server as a subprocess (via MCPClient), and wires Claude, CliChat, and CliApp together.
  • The MCP server runs out-of-process, communicating with MCPClient over stdio using MCP's JSON-RPC protocol (stdio_client + ClientSession). This isolates tool execution from chat/agent logic and lets multiple servers plug in side by side (see clients: dict[str, MCPClient] in main.py).
  • Only Claude talks to the Anthropic API; only MCPClient talks to the MCP server. Chat/CliChat sit in between and never call either directly.

03 File-by-file breakdown

main.pyComposition root / entry point
  • Loads .env (CLAUDE_MODEL, ANTHROPIC_API_KEY) via dotenv.
  • Instantiates Claude(model=claude_model).
  • Uses an AsyncExitStack to start the document MCP server as a subprocess (python mcp_server.py or uv run mcp_server.py) wrapped in an MCPClient named doc_client.
  • Accepts extra server scripts via sys.argv[1:], each spun up as its own MCPClient and added to a clients dict — the extension point for plugging in more MCP servers without touching the agent loop.
  • Builds CliChat(doc_client, clients, claude_service) and CliApp(chat), calls cli.initialize() then cli.run().
  • On Windows, sets the Proactor event loop policy (required for subprocess stdio pipes with asyncio).
mcp_client.pyMCPClient — protocol adapter
  • connect() — builds StdioServerParameters, opens the stdio transport, opens a ClientSession on top, calls session.initialize() (the MCP handshake).
  • list_tools() / call_tool(name, input) — tool discovery & invocation.
  • list_prompts() / get_prompt(name, args) — prompt discovery & rendering.
  • read_resource(uri) — reads an MCP resource; JSON mime type is parsed, otherwise returned as raw text.
  • Implements __aenter__/__aexit__ so it can be used as an async context manager (as main.py does via AsyncExitStack); cleanup() tears down the subprocess/session.
  • One MCPClient instance = one connection to one MCP server subprocess.
mcp_server.pyThe MCP server (subprocess)

Built on FastMCP. Holds docs: dict[str, str] as a fake in-memory store, exposed via three MCP primitives:

  • Tools (callable by Claude, dispatched through ToolManager): read_doc_contents(doc_id), edit_document(doc_id, old_str, new_str).
  • Resources (read directly by the client): docs://documents (JSON list of ids, used for @ autocomplete), docs://documents/{doc_id} (raw text of one document).
  • Prompts (triggered by /command): format(doc_id) returns a canned instruction telling Claude to rewrite the doc as Markdown using edit_document.

mcp.run(transport="stdio") starts the server reading/writing MCP JSON-RPC over stdin/stdout — this is what MCPClient.connect() talks to.

core/claude.pyClaude — Anthropic SDK wrapper
  • chat(messages, system, temperature, tools, thinking, ...) → calls client.messages.create(...), optionally attaching tools, system prompt, or extended-thinking params; returns the raw Message.
  • add_user_message / add_assistant_message → append normalized {role, content} dicts to a running messages list.
  • text_from_message(message) → concatenates all text-type content blocks into one string, ignoring tool_use/thinking blocks.
  • This is the only module that talks to the Anthropic API.
core/tools.pyToolManager — Claude ↔ MCP bridge
  • get_all_tools(clients) → calls list_tools() on every connected MCPClient and flattens results into Anthropic's tool schema (name, description, input_schema) — this list becomes tools= in Claude.chat.
  • _find_client_with_tool(clients, tool_name) → searches all clients to find which MCP server owns a tool name, so multiple servers can coexist without name-routing config.
  • execute_tool_requests(clients, message) → pulls every tool_use block out of Claude's response, resolves its owning client, calls call_tool(name, input), and packages the result as an Anthropic tool_result block. Returns the blocks to be sent back to Claude as a user message.
core/chat.pyChat — the agent loop

Base class implementing the core think → act → observe loop:

  1. _process_query(query) — appends the raw user query as a user message (overridden by CliChat).
  2. run(query) loops: call claude_service.chat(...) → append assistant response → if stop_reason == "tool_use", execute tools via ToolManager and append results as a new user message, then loop again; otherwise extract final text and return.

This loop is what lets Claude chain multiple tool calls (read a doc, edit it, read it again) before producing a final answer.

core/cli_chat.pyCliChat(Chat) — document-aware specialization
  • Holds a dedicated doc_client; exposes list_prompts(), list_docs_ids(), get_doc_content(), get_prompt() as passthroughs, used by CliApp for autocompletion.
  • _extract_resources(query) — scans for @word mentions, checks each against the real doc id list, fetches matching documents, formats them as <document id="...">...</document> blocks.
  • _process_command(query) — if the query starts with /, treats words[0] as an MCP prompt name and words[1] as doc_id, calls doc_client.get_prompt(...), converts the returned PromptMessages into Anthropic message params, and appends them directly to self.messages — bypassing the normal wrapper prompt.
  • _process_query(query) (override) — if it wasn't a /command, wraps the query and any @mention content into one instruction prompt telling Claude how to use the inlined context.
  • Module-level helpers convert_prompt_message(s)_to_message_param adapt MCP's PromptMessage shape into the plain dicts the Anthropic SDK expects.
core/cli.pyCliApp — terminal front-end

Built on prompt_toolkit, purely presentational — no chat/business logic:

  • UnifiedCompleter — suggests document ids after @, /command names after / (with description), and a doc id argument once a valid /command  is typed.
  • CommandAutoSuggest — inline grey-text suggestion of the expected argument name (e.g. doc_id) right after typing a known command.
  • Custom KeyBindings for /, @, and space auto-open completion menus, mimicking Slack/Discord-style slash commands.
  • initialize() → refresh_resources() + refresh_prompts() once at startup to populate the completer.
  • run() → the REPL: reads a line, ignores blank input, calls agent.run(user_input) (inherited Chat.run), prints the response; Ctrl+C exits.

06 Mental model summary

Host = main.py process Client = MCPClient Server = mcp_server.py Agent loop = Chat.run
  • Host = the whole main.py process (CLI + agent + Claude wrapper).
  • Client = MCPClient — one per MCP server connection, purely a protocol adapter (stdio JSON-RPC ↔ Python async calls).
  • Server = mcp_server.py — owns the actual data (docs dict) and business logic, exposed as tools/resources/prompts.
  • Agent loop (Chat.run) is model-driven orchestration: it doesn't know about documents at all — it only knows "call Claude, and if it asks for tools, run them via ToolManager and feed results back."
  • CliChat is where document-specific UX lives: @mention inlining and /command dispatch are client-side conveniences built on top of generic MCP resource/prompt primitives — Claude itself never sees the raw @// syntax, only pre-resolved context or prompt messages.
  • CliApp is purely presentational (prompt_toolkit REPL + autocomplete) and holds no chat/business logic — it only calls into CliChat.
  • Extensibility: additional MCP servers can be attached by passing extra script paths as CLI args to main.py; ToolManager automatically discovers and routes to their tools with no other code change.
